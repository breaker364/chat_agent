# 第一部分 项目介绍

## 1. 30 秒开场版

面试官您好。这个项目是我在蔚来智能制造集成部门期间，面向部门自动化办公处理场景开发的一个 AI 办公 Agent 系统。背景是部门日常有大量重复性的文档和数据处理工作——整理文档、处理表格、跨系统汇总信息、写报告、查资料——这些工作流程固定但繁琐。这个系统让用户用自然语言描述需求，由 Agent 自己拆解任务、调用工具、执行并交付结果。

技术上是前后端完整的一套：后端 FastAPI 加 LangGraph 做 Agent 编排，前端 React 加 Vite，通过 SSE 流式看到整个执行过程。能力上覆盖任务规划、多 Agent 协作、RAG 知识库、联网搜索、Python 和 Shell 脚本执行、长上下文压缩等。这个项目我重点解决的不是"能不能调通模型"，而是"怎么把模型能力做成可靠、可控、可追踪的办公自动化系统"。

## 2. 业务背景：为谁解决什么问题

（面试官问"项目背景 / 为什么做这个 / 你的角色"时用。这段要讲出业务痛点，让项目有落地感。）

我所在的是智能制造集成部门，日常工作和"集成"两个字强相关：要对接多个系统的数据、处理各种格式的文档、维护多维表格、输出各类报告。具体痛点有这么几类：

第一，文档处理量大且格式杂。PDF、Word、Excel、PPT 之间的内容提取、转换、汇总，人工做就是反复复制粘贴。

第二，信息分散在多处。内部资料在飞书文档和多维表格里，外部信息要联网查，一份报告经常要跨五六个来源汇总，人来回切换很低效。

第三，很多流程是"固定套路"：拿到数据、按模板处理、生成表格或文档、发到指定位置。这类工作规则明确、重复度高，正是自动化收益最大的地方。

当时的思路是：与其针对每个场景写死一个自动化脚本，不如做一个通用的 Agent 底座——把文件读写、Python、Shell、检索这些原子能力做成工具，让大模型根据需求自己规划怎么组合。这样新场景不用开发，用一句话描述需求就能执行；规则复杂、稳定的场景再沉淀成技能，长期复用。

我的角色是这个系统从零到一的设计和开发：整体架构、Agent 编排、工具体系、RAG、上下文管理、前端交互都是我做的。

## 3. 一到两分钟完整版

（比 30 秒版更展开，适合"详细介绍一下你的项目"。用一个典型办公场景串起全部机制。）

举一个部门的典型场景：用户说"把这周上传的项目文档汇总成一份进展报告，和知识库里的历史方案做对比，再查一下行业标准有没有更新，最后生成 PPT 放到工作区"。这个请求进来之后，系统是这样工作的：

第一步，进入 FastAPI 服务层。系统按会话做互斥控制，同一会话同一时间只跑一个前台任务，避免两轮回答交叉写坏历史；每次运行分配 run ID，所有事件靠它归属。

第二步，模型先做任务规划：把这个复杂需求拆成一份带状态的任务清单——解析文档、检索知识库、联网调研、撰写报告、生成 PPT——每完成一项更新一次状态，用户在前端能实时看到"做到哪一步了"。

第三步，按计划执行。需要事实证据的部分走一个受约束的调研流程（Agentic Research）：先定研究计划，再按调用次数和时间预算去知识库和网页采集证据，采完评估"够不够、要不要换来源"。知识库这边是完整 RAG 链路：结构化分块、关键词加向量双路召回、融合重排、带引用返回。

第四步，重活交给代码执行。整理 Excel 数据、批量转换文档格式这类事，模型会写 Python 脚本并用内置的执行工具跑，跑错了看报错自己修；系统级的文件操作用受控的 Shell 工具完成。期间如果上下文太长，系统会自动把历史压缩成结构化摘要，保证长任务不会撑爆模型窗口。

整个过程中每一步——模型说了什么、调了什么工具、结果是什么——都通过 SSE 实时推给前端，同时持久化到会话文件，中途刷新或重启都能恢复。

总结来说，这个项目的核心挑战是把"模型能干活"工程化成"干得可控、可追踪、可恢复"：自主性有边界（规划、预算、沙箱）、过程可观测（事件流、任务清单、审计）、结果可信赖（引用、幂等、变更核验）。目前是单进程文件存储形态，生产化需要补什么我也清楚，可以展开聊。

## 4. 整体架构与一次请求的生命周期

（这一节是全文档的"地图"，后面每章都是对其中一段的展开。被问"讲一下整体架构"先画这条链。）

```text
React/Vite 前端
   │  POST /chat/stream（fetch 读 ReadableStream，解析 SSE）
   ▼
FastAPI 服务层
   ├─ 会话级运行互斥（同会话同时只有一个前台 run，冲突返回 409/错误事件）
   ├─ 分配 run_id，所有事件带 session_id + run_id 归属
   ├─ 可选：Agentic Research 证据协调（plan → collect → assess，有预算）
   ▼
LangGraph ReAct 主循环：模型 ↔ 工具，循环直到产出最终回答
   ├─ 任务规划：任务清单工具，拆步骤、标状态、随事件推给前端
   ├─ 工具层：文件读写、bash、python 执行、网页搜索、知识库、视觉
   ├─ 多 Agent：主 Agent 派生子 Agent（独立提示词、工具权限、后台运行）
   ├─ 技能系统：SKILL.md 声明式扩展（PDF、PPT、Excel、架构图、飞书等）
   └─ 上下文管理：token 监控 → 历史压缩 → 关键内容再注入
   ▼
SSE 事件流实时推送 + 会话历史持久化（JSON/JSONL）+ 工具审计记录
```

用一句话串起来：**请求进来先过会话互斥和 run 归属，模型规划任务清单，需要证据的走有预算的调研协调，然后在 ReAct 循环里调工具执行，全程事件流式推送并持久化，最终回答带引用返回。**

## 5. 工具与机制清单

（面试官问"Agent 都有哪些工具/能力"时，按这组讲，每个先说"是什么、解决什么"，一句机制。）

**任务规划（Plan）**：参考了 Claude Code 的 TodoWrite 机制。接到复杂任务时，模型先把需求拆成任务清单，每次更新是全量快照，任何时刻恰好只有一个任务处于进行中；清单状态随事件推给前端展示进度，并随会话持久化，中断恢复后还能看到全局进展。它的价值是把"长任务的失控感"变成"可看见的推进"。

**多 Agent（子 Agent）**：主 Agent 可以派生子 Agent 来干独立的活。每个子 Agent 有独立的系统提示词和工具权限（白名单/黑名单控制它能用哪些工具），跑在后台线程，不阻塞主对话；主 Agent 和它之间用信箱通信，可以发消息、查状态，有最大运行时长限制。典型用法是把耗时或需要隔离权限的子任务外包出去。

**上下文压缩**：办公处理任务动辄几十轮工具调用，上下文很快超限。系统持续做 token 估算，接近模型窗口上限时自动触发压缩：按用户轮次切分历史，把旧的原始对话压成固定结构的摘要（事实结论、文件产物、未完成项、工具证据），URL、路径、版本号这类不能被改写的字面量单独记在"精确账本"里；压缩后的关键上下文再通过附件机制注入回来。这样长任务不丢关键事实，也不中断。

**bash**：受控的 Shell 工具，用于系统级操作和脚本调用。默认关闭，启用后有多层约束：可执行文件白名单、工作目录限定在工作区、环境变量白名单、超时控制、输出截断、超时后清理整棵进程树。敏感信息会在输出里做脱敏。

**Python 执行**：工具是"写脚本再执行"的模式——模型把数据处理逻辑写成 .py 文件，用执行工具运行，拿到 stdout 和报错后自行修正重试。执行有超时上限，可以指定工作目录和 Python 解释器；知识库内部索引被隔离保护，必须走检索工具访问而不是被脚本绕过。办公场景里 Excel 清洗、批量格式转换、数据统计都靠它。

**RAG 知识库**：两阶段流程——导入只登记文件，同步才做解析、结构优先分块、BGE-M3 向量化入 Qdrant、建 BM25 索引。检索时关键词和向量双路召回，RRF 融合，再经本地 reranker 精排，回答带引用出处。Embedding 和重排都是本地模型，部门内部资料不出域。还有知识策略控制：auto 由 Agent 自主决定、required 强制必须引用知识库、disabled 禁用。

**网页搜索（WebSearch）**：搜索后端做了适配器抽象，Bing、Tavily 可以配置切换，带 TTL 缓存避免重复搜索。它是调研流程的证据来源之一，和知识库在同一个"来源路由"体系里被统一调度，而不是模型想搜就搜。

**其他能力**：文件工具（读、写、glob、grep，全部限制在工作区沙箱内，外部目录需显式配置为只读）；图片视觉理解；技能系统（SKILL.md 声明式扩展，内置 PDF、PPT、Excel、架构图生成和飞书集成）；飞书集成（扫码登录后可读写飞书文档和多维表格，办公数据的出入通道）；跨会话持久记忆（自动提炼用户偏好和项目背景，供后续会话复用）。

## 6. 这个项目里我认为有难度、值得展开的点

（主动抛出，引导面试官往准备好的方向问。）

1. **流式链路的事件设计**：一个请求产生多类事件（文本、工具调用、工具结果、任务清单、研究进展、调试），怎么设计事件协议让前端稳定消费、怎么归属到会话和 run。
2. **上下文压缩的"有损但可信"**：压缩历史本质有损，怎么用固定摘要结构加字面量账本让关键事实不丢、不被模型改写，怎么做缓存校验避免重复压缩。
3. **工具可靠性**：LLM 重复发起同样调用很常见，怎么通过参数归一化识别"语义相同"的调用，只读和写操作怎么区别对待，写操作怎么做幂等和变更核验。
4. **受约束的自主性**：Agent 的自主和可控是矛盾的——任务规划给全局可见性、调研预算管资源消耗、工具白名单管权限、沙箱管边界，都是在给自主性画边界。
5. **真实环境的工程细节**：比如 Windows 下会话文件被占用时的替换重试、本地大模型的加载与显存权衡，这类真实踩坑问题。

## 7. 主动讲边界（加分项，建议每场面试至少讲一次）

（主动说清当前边界，比被面试官戳穿可信得多。）

- 当前是**单进程文件存储**形态：运行互斥锁、调用缓存、压缩锁都是进程内的，多 worker 或多实例部署要换成 Redis 租约或数据库约束，方案我清楚。
- SSE 是**尽力而为**推送：断线重连后前端会重新拉取会话历史对齐状态，但还没有完整的可重放事件协议（序号、Last-Event-ID）。
- 工具去重是**应用层 best effort**，不是 exactly-once；跨进程、崩溃恢复场景需要业务幂等键或持久化状态机。
- 检索质量评测框架已搭好，但完整的离线指标结论还需要补实验。
- 认证和多用户隔离没做：持久化记忆和知识库的作用域是受信任工作区，不适用于未经隔离的多用户部署；办公场景里凭证全部走本机配置，不落代码和日志。

（讲边界的正确姿势：说"我知道它现在的形态、生产化要补什么、怎么补"，体现判断力，而不是示弱。）

## 2.2 LangGraph 编排：两层图

**完整版：**

我们的 LangGraph 编排是"两层图，按任务复杂度分流"。简单对话走第一层：直接用 LangGraph 预制的 create_react_agent，图结构就是"模型到工具再到模型"的循环，模型决定调什么工具、拿到观察结果继续推理，直到给出最终回答；通过 astream_events 把图内部的模型和工具事件桥接成应用的 SSE 事件流，并用 recursion_limit 180 做步数安全阀，防止循环失控。复杂任务走第二层：一个自建的固定拓扑 StateGraph 父图，节点链路是 intake 做请求接入、prepare_context 准备上下文、route 做路由决策——路由受策略约束，只能提议预先授权过的能力范围；然后 planner 产出有界任务 DAG，plan_guard 对计划做校验，approval_gate 是一个审批关卡，用了 LangGraph 的 interrupt 原语做人工确认；通过后 scheduler 调度就绪任务，dispatch_task 用 Send 原语把独立任务并行派发出去，join 汇合结果，再经 assess 评估、validate 校验、finalize 收尾，另外还有 direct_executor 和 clarification_gate 两个快捷分支绕过长流程。每个任务再进入对应的子图：research 类任务进研究子图，只读、带调用预算，走计划、采集、评估三段；execute 类任务进执行器子图，是一个工具按能力裁剪过的受限 ReAct 循环。工程上有三个值得说的点：一是状态设计，状态用 TypedDict 定义，消息用 add_messages 累加，任务结果和证据用了自定义 reducer 做合并，保证 Send 并行派发时状态合并不冲突；二是容错，模型规划失败时有一个确定性的兜底 planner，保证流程不中断；三是所有 LangGraph API 的引用收敛在 workflow_compat 一个兼容层里，框架升级只改一处。整个编排的设计理念就是"给自主性画边界"：路由限能力、计划过守卫、审批用 interrupt、每个子任务有各自的步数和预算上限。

**极简版：**

简单任务走 LangGraph 预制的 ReAct 图，模型和工具循环加步数上限；复杂任务走自建的固定拓扑父图，路由限定能力、规划器产出任务 DAG、interrupt 做人工审批、Send 并行派发子任务到研究子图或受限执行器子图，最后汇合评估收尾，并行合并靠自定义 reducer 保证安全。

**追问兜底：** 如果被问"两层图怎么选的"——答案是配置开关（workflow config 的 enabled）加路由节点决策，不是纯自动判断，不要把话说满。

## 2.3 LangGraph 状态定义

**完整版：**

我们的状态定义是"分层 TypedDict 加自定义 reducer"的思路，分三个层级。最简单的主 ReAct 图直接用预制图内置的消息状态，消息列表用官方的 add_messages reducer 做累加。复杂任务的自建父图则是完全自己定义的 WorkflowState：主体是 TypedDict、total=False，意味着每个节点只返回增量字段，图引擎负责合并，不用传全量状态；字段按阶段分组，每一组又是一个独立的嵌套 TypedDict——request 是请求上下文（会话、run、知识策略），route 存路由决策（模式、所需能力、风险级别、是否需要审批），plan 是计划快照（版本号、任务列表、是否校验通过），task_results 按任务 ID 存各任务结果，artifacts 存产物引用，errors 和 events 是错误和审计事件，control 是预算控制，approval 存审批状态。这个状态设计里最核心的是自定义 reducer，它解决的是 Send 并行派发带来的写入冲突问题：多个子任务并行返回时，默认的覆盖式更新会互相冲掉，所以我们给 task_results 写了按 task_id 合并的 reducer，并且用 attempt 序号做保护——晚到的旧尝试不能覆盖更新的结果；evidence 的合并是内容寻址去重，每条证据的 key 用显式 ID 或者来源加内容摘录的 SHA256，保证并行采集的同一条证据只留一份；errors 和 events 用有界合并，分别只保留最近 100 条和 200 条，防止长流程把状态撑爆。另外有两个工程细节：一是 control 字段把最大任务数、最大并行数、最大重试次数、最大重规划次数直接作为状态流转，预算不是写死在节点里而是跟着状态走；二是状态里带 schema_version 字段、checkpoint 线程 ID 按"会话：run"拼接隔离，为状态演化和断点恢复留了口子。总结一句话：状态不只是传数据的容器，它被设计成整个工作流的"协议加审计日志"——类型化保证了节点间契约，reducer 保证了并行安全，有界合并和审计事件保证了可回溯。

**极简版：**

状态是 TypedDict 定义、total=False，节点只回增量；字段按阶段分组成嵌套结构（请求、路由、计划、任务结果、产物、错误、审计、预算控制）；核心是自定义 reducer——任务结果按任务 ID 加尝试序号合并防止乱序覆盖，证据按内容哈希去重，错误和事件有界保留，配合内置 add_messages 管消息，整体上状态同时承担数据传输、并行安全和审计追溯三个职责。

**追问兜底：** 被问"为什么用 TypedDict 而不是 Pydantic"——诚实答案是 TypedDict 是 LangGraph 官方示例的惯用法、类型检查够用且零运行时开销；想讲得更好可以补一句"代价是运行时不做校验，校验放在了 plan_guard 这类节点里显式做"。

## 2.4 任务规划（Plan）机制

**总起一句**：plan 机制参考了 Claude Code 的 TodoWrite，解决的是长任务"做到哪了、断了从哪续"两个问题。

**数据层**

- 工具是 `update_task_plan`，每次提交全量快照，不做增量 patch；
- 每项五要素：task_id、content（祈使句描述做什么）、activeForm（进行时措辞，执行中给前端展示）、status（pending / in_progress / completed / failed / blocked）、result_ref（产物引用）。

**约束层（执行纪律，工具层强校验）**

- 至多一个 in_progress，违反直接报错拒绝；
- 计划一旦建立，任务列表就固定了——后续只能更新"最靠前的未完成项"的状态、详情和产物引用，不能加任务、删任务、改范围；
- 已完成项不可降级、不可删除，防止模型偷改历史把没做的标成做完。

**持久化与展示层**

- 计划落盘为会话目录下的 task_plan.json 加 jsonl 追加日志，服务重启、会话恢复后 unfinished 项直接读回来，提示模型"从持久化计划继续，别重头再来"；
- 每次更新随 SSE 推给前端，用户实时看到进度，中断恢复也有全局锚点。

**设计理念一句**：它本质是给模型加"外部工作记忆"——模型上下文可能被压缩、可能跑偏，但计划在磁盘上，纪律在工具校验里，不依赖模型自觉。

**追问兜底：** 被问"模型不写计划怎么办"——系统提示词引导复杂任务先建计划，但这是引导不是强制；强制的部分只有约束层那三条校验。

## 2.5 多 Agent 协作（子 Agent）

**总起一句**：主 Agent 可以把子任务外包给带独立提示词和受限工具的子 Agent，后台执行、信箱通信，主对话不被阻塞。

**定义与权限层**

- 子 Agent 由三要素定义：agent_type、when_to_use（什么时候派它）、独立 system_prompt；
- 工具权限用白名单加黑名单双重过滤，典型如 Explore 型子 Agent 禁用所有写工具和再派生能力（不能再派孙 Agent），只读执行；
- 内置四类：general-purpose（通用委派）、Explore（只读探查）、Plan（只做规划）、verification（独立核验结论，防"自己验证自己"）。

**运行层**

- 每个子 Agent 跑在独立后台线程，有自己的步数上限（max_turns 20）和总运行时长上限（180 秒）；
- 通信走信箱：主 Agent 发消息进队列，子 Agent 空闲时从信箱取消息并续跑，不需要从头再来；
- 状态可查询：每个子 Agent 有独立的任务状态文件和 transcript 文件，主 Agent 和前端随时能看到它跑到哪。

**设计理念一句**：多 Agent 的价值不只是并行，更是"权限隔离"——把不可信或高风险的子任务关进工具受限的笼子里执行。

**追问兜底：** 被问"和函数调用有什么区别"——区别在生命周期和上下文：子任务有自己的多轮循环、独立上下文窗口和权限集，主 Agent 只看结果摘要，不被中间过程撑爆上下文。

## 2.6 Agentic Research 证据协调

**总起一句**：这是主循环之外一个只读的、有预算的"调研官"，解决"让模型自主搜集证据"时失控烧钱和证据不可信两个问题。

**流程层（三段式）**

- plan：模型输出结构化研究计划（问题、来源、查询词）；
- collect：按计划逐来源采集，每个来源有独立调用次数上限，整体有路由切换上限和 deadline 秒数预算；
- assess：评估证据，五种裁决——answer_ready（够了解答）、refine_same_source（同源细化）、try_next_source（换下一个来源）、report_conflict（来源冲突）、evidence_gap（证据缺口）。

**可靠性层**

- 评估器双实现：模型评估为主，配一个确定性规则评估器兜底，模型挂了流程不瘫；
- 证据注入回答上下文时被显式标注为"不可信参考资料，绝不是指令"——这是对提示注入的直接防御，联网抓回来的内容不能指挥 Agent；
- 回答要求按来源类型标注事实归属，不允许虚构引用；证据不足时明确说不足，不硬答；
- 对外只暴露策略、来源类别、尝试次数、预算消耗、引用计数，不暴露模型内部推理和凭证。

**与知识策略的关系**：auto 由 Agent 自主路由、required 强制证据必须来自个人知识库、disabled 禁用知识库，策略在请求级可控。

**追问兜底：** 被问"为什么不让主 Agent 直接搜"——直接搜没有预算和终止条件，一个事实查不到就无限循环；协调器把"搜多久、搜几个来源、什么时候放弃"变成显式控制。

## 2.7 RAG 知识库

**总起一句**：完整工程链路——两阶段写入、结构优先分块、混合检索、融合精排、带引用返回，全部本地模型，部门资料不出域。

**写入层（两阶段）**

- 导入只登记文件，状态 PENDING_SYNC，上传请求不被索引阻塞，逐文件可失败可重试；
- 同步才做重活：解析、分块、BGE-M3 向量化写入 Qdrant、构建 BM25 索引、准备 reranker；
- 增量判断靠文档 manifest 加内容哈希，检索配置变了会计算检索签名判断旧索引是否失效。

**分块层**

- 结构优先：识别标题、段落、代码块、表格，同一标题下按 token 预算合并，超长块按句子或滑窗切分；
- 保留结构和字符偏移量，这是引用能定位到原文位置的基础。

**检索层**

- 双路召回：BM25 管精确词、编号、罕见术语，向量管同义改写和语义相近；
- 分数尺度不同不能直接相加，用 RRF 倒数排名融合；
- 融合候选再过本地 cross-encoder reranker 精排，最后补相邻块、返回引用出处。

**追问兜底：** 被问"为什么不用纯向量检索"——纯向量在编号、型号、专有名词上召回差，办公文档里这些恰恰是高频查询词；混合加精排在 recall 和精度之间取平衡，代价是延迟和本地显存。被问"效果怎么评估"——离线评测框架已搭好（标注问题集、分阶段召回率），完整指标结论是待补的实验，不要报具体数字。

# 第三部分 高频追问与回答要点

（每题先给结论句，再给展开点。回答模板：结论，代码证据，取舍，边界，下一步。）

**Q1 为什么用 LangGraph，不自己写循环？**

- 结论：循环本身好写，难的是状态管理、断点恢复、并行合并和事件流，图框架把这些标准化了；
- LangGraph 给了状态 reducer、checkpoint、Send 并行、interrupt 审批这些原语，自己写等于重造；
- 同时所有框架 API 收敛在一个兼容层，保留随时替换的自由。

**Q2 recursion_limit 能防止任务卡死吗？**

- 结论：不能，它只限图步数，不限墙钟时间，也中断不了已发出的模型或子进程调用；
- 真正防卡死需要组合拳：每步超时、总 deadline、进程树清理、取消传播；
- 主动承认：当前部分超时已实现，完整 deadline 机制是待生产化项。

**Q3 SSE 断线会不会丢消息或重复？**

- 结论：当前是尽力而为——前端断线后会重拉会话历史对齐状态，但不是完整的可重放协议；
- 生产化路径：递增事件序号、Last-Event-ID、事件日志重放窗口；
- 关键认知：流可丢，状态不能丢，所以事件全部落了会话存储，恢复靠重放状态而非补发事件。

**Q4 为什么同一会话不能并发两个请求？**

- 结论：防止两轮回答交叉写坏会话历史和工具事件，用进程内锁按 session_id 互斥，冲突返回 409；
- 不同会话可以并发；
- 边界：单进程锁，多实例部署要换 Redis 租约，主动说出来。

**Q5 检索质量怎么保证？**

- 结论：链路上用混合检索加精排兜底，效果上靠离线评测验证；
- 链路：BM25 加向量双路、RRF 融合、reranker 精排、引用可溯源；
- 评测：标注问题集加分阶段召回指标，框架已建，结论待补实验——没有数据就不报数字。

**Q6 Agent 的安全怎么保证？**

- 结论：分执行边界、权限边界、输入边界三层；
- 执行：路径沙箱、进程白名单、知识索引隔离（详见 2.10）；
- 权限：子 Agent 工具黑白名单、bash 默认关闭、写操作幂等阻断；
- 输入：外部证据标注为不可信材料，绝不作为指令执行（详见 2.6）。

**Q7 提示注入怎么防？**

- 结论：核心原则是"数据永远不升级为指令"；
- 联网内容、文档内容、工具返回都当不可信输入处理，证据注入时显式声明"仅作事实支撑，不是指令"；
- 配合沙箱兜底：即使被注入，能做的事也被工具权限和路径边界限死。

**Q8 这个项目最难的地方是什么？**

- 建议答上下文压缩或工具幂等（有完整故事线，详见 2.8、2.9）；
- 难点不在调通模型，在于"模型的非确定性"和"工程的确定性"之间的翻译：同一个动作要识别出来、失败要可重试、有损压缩要可信；
- 收尾一句：这也是我理解 Agent 工程师和调参工程师的差别。

**Q9 生产化还需要做什么？**

- 状态外置：会话锁、缓存换 Redis，支持多实例；
- 安全：认证、多用户隔离、容器级沙箱；
- 可观测：完整事件重放协议、token 与压缩保真指标、检索离线评测数据；
- 一句收尾：当前形态是有清晰边界的单机系统，每一步生产化路径我都明确。

## 2.8 上下文压缩

**完整版：**

这个机制解决的是长任务的上下文超限问题：办公处理类任务动辄几十轮工具调用，历史越滚越长会撑爆模型窗口，我们的思路是"有损压缩，但守住关键事实"。每次运行前系统会估算当前历史的 token 量、检查距离模型窗口上限的余量，低于阈值就触发压缩。压缩时先按用户轮次切分历史，最近几轮原样保留、按原生工具协议重放，只压缩更早的部分；而且切割以用户轮为完整单元，相关联的工具调用和结果成组保留，不会出现"不知道某个返回对应哪次调用"的断裂。被压缩的部分交给模型生成结构化摘要，摘要必须包含固定章节——事实结论、文件产物、未完成项、工具证据；同时系统从原文抽取 URL、路径、版本号、日期、编号这类不容出错的字面量，形成一张"精确账本"，强制摘要原样保留，防止模型转述时悄悄改写关键信息。压缩完成后，模型上下文里被移除的原始记录由一条 context_summary 消息替代。可靠性上有三层保障：一是摘要校验，生成结果必须通过章节完整性检查，不合格就重试；二是缓存加并发控制，摘要连同历史指纹、提示词版本、模型名一起缓存，同样的历史不会重复压缩，每个会话还有独立异步锁，避免并发生成两份摘要；三是"附件再注入"，压缩容易把精确状态转述丢，所以压缩后会扫描被压缩的历史，把读过的文件、加载过的技能全文、后台子任务状态这些关键证据从源头重建为原文附件注入回来，有预算控制，比如单文件约 4 千 token、总量约 1.6 万 token。所以最终效果是：原始记录丢弃、事实保留，长任务能持续跑而不丢关键上下文。当前边界是 token 用的是通用估算，和目标模型的真实 tokenizer 有偏差，生产化应该换成官方 tokenizer。

**极简版：**

长对话接近模型窗口上限时，把旧轮次按用户轮成组压缩成固定结构的摘要，URL、路径、版本号这类字面量进精确账本防改写，最近几轮原生保留；摘要校验通过并带指纹缓存，压缩后再把读过的文件、技能内容等关键证据从源头原文注入，做到"原始记录丢弃、事实保留"。

## 2.9 工具调用去重与幂等

**完整版：**

这个机制解决的问题是：LLM 经常会重复发起语义相同的工具调用——重试、改写措辞再调、或者用户重发——只读调用重复是浪费钱和延迟，写调用重复就是重复建文档、重复写表格这种真实事故。我们的方案分四层。第一层是"识别语义相同"：调用进来先做参数归一化——文件路径转成工作区相对表示、大段内容转成哈希、默认值和列表项做规范化——然后序列化成 canonical JSON 拼上工具名算出调用 key，这样参数顺序不同、路径写法不同的"同一个动作"会算出同一个 key。第二层是按工具性质分类处理：每个工具先被标记为只读可缓存、有副作用、仅审计三类；同一个 run 内相同 key 的调用直接复用已有结果，而且并发场景做了 single-flight——相同调用同时到达时，后到的挂在一个事件上等第一个执行完直接拿结果，不会真跑两遍；只读工具的结果还会带 TTL 存进会话级缓存跨轮复用，只缓存成功结果，失败结果用短 TTL 防止把坏结果缓存住。第三层是副作用工具的硬阻断：写操作第二次以相同参数进来时根本不会执行，直接返回一个结构化阻断消息——标记 duplicate_side_effect_tool_call、不可重试，并附上一个 action_id，也就是工具名加归一化参数算出的确定性动作身份——告诉模型这个动作已经执行过了，要再做需要用户显式确认。第四层针对飞书 CLI 这类远程命令，做了更完整的动作级幂等：把命令解析成一份与具体服务商无关的规范化变更清单——操作对象、目标、操作类型、是否变更型、幂等输入、验证模式——执行后有变更核验确认写操作真的生效，配合错误分类体系判断失败可不可重试，避免"超时重试结果其实已经成功"这种经典的重复写。另外每次调用包括被阻断的都会记审计：参数哈希、是否复用、来源、耗时。边界也说清楚：这是应用层的 best effort，不是 exactly-once——缓存和锁都在单进程内，多实例部署或进程崩溃恢复场景，需要持久化的幂等键或业务层状态机兜底。

**极简版：**

先把工具参数归一化成规范 key 识别"语义相同"的调用；只读工具结果带 TTL 复用、并发相同调用合并成一次执行；有副作用的工具相同参数绝不二次执行，直接返回带 action_id 的阻断消息要求用户确认；远程写命令还有变更清单、执行后核验和错误分类，整体是应用层 best effort 的幂等，不是 exactly-once。

**追问兜底：** 被问"action_id 为什么是确定性的"——它由工具名加归一化参数哈希而来，同样的动作在任何时候算出同一个 ID，这样不依赖内存状态也能判断"是不是同一个动作"，这是往持久化幂等演化的基础。

## 2.10 沙箱机制

**总起一句**：沙箱的目标是让 Agent 拥有"够用的文件和执行能力，但越不出边界"，全部在应用层实现，分三层。

**第一层：文件路径边界（最核心）**

- 所有文件工具的路径先 resolve 再校验，绝对路径相对路径统一处理，必须落在工作区根内，`..` 穿越、越界路径直接 PermissionError；
- 读比写宽：外部目录可以显式配置成"只读根"，可读、可复制进工作区，但不能写；写只能写工作区内部；
- 受管目录单独保护，比如持久记忆目录，工作区内的其他工具也禁写，只有记忆服务自己能碰。

**第二层：专属通道隔离**

- 知识库索引对文件工具和 Python 脚本完全不可见，必须走 knowledge_search 工具，防止脚本绕过检索和权限体系；
- 技能的托管脚本不允许用 bash 或 Python 直接执行，必须走技能的正规执行通道。

**第三层：进程执行约束**

- bash 默认关闭，启用后四重限制：可执行文件白名单、工作目录限定在工作区内、超时控制、输出截断，超时杀整棵进程树，输出里的敏感值还会脱敏；
- Python 执行只能跑 .py 文件，有超时上限，同样受知识索引隔离约束；
- glob/grep 这类检索工具只返回工作区相对路径、结果条数有界。

**边界一句**：这是应用层沙箱，不是容器级隔离——防的是模型行为越界，不防恶意原生代码逃逸，生产化如果要跑不可信代码，应该上容器或微虚拟机。

**追问兜底：** 被问"为什么不上容器"——场景是受信任的个人办公环境，应用层边界加审计已够用，代价小；如果开放多用户或执行外部代码，容器化是第一步。
