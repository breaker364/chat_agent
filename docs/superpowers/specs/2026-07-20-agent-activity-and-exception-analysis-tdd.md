# Agent 工作动态与异常分析 TDD 方案

## 适用范围

本文档对应 OpenSpec 变更 `improve-agent-activity-and-exception-analysis`，覆盖以下两项能力：

- 基于执行证据的异常分析与安全兜底。
- 面向用户的实时 Agent 工作动态时间线。

本文档只定义测试优先的实施顺序，不替代 OpenSpec 的需求、技术设计和任务清单。

## 不可违反的规则

每一个生产行为必须严格经过 Red -> Green -> Refactor：

1. 先写一个只描述单一行为的测试。
2. 运行该测试，确认它因功能尚未实现而失败，而不是因拼写、导入或测试环境错误而失败。
3. 只写使该测试通过的最小生产代码。
4. 重跑该测试及相关测试，确认全部通过。
5. 只有全部为绿后，才能消除重复或提取辅助函数；重构后再次运行测试。

不得先写实现、再补测试；不得以人工验证替代 Red 阶段；不得为了让测试通过而把测试断言改弱。

## 测试运行环境的 Red 阶段

当前项目未提供后端测试目录或前端测试脚本。因此，第一轮测试只建立最小、可重复执行的环境：

| 顺序 | 先写的失败测试 | 预期失败原因 | 最小 Green 改动 |
| --- | --- | --- | --- |
| 0.1 | `backend/tests/test_agent_activity.py` 中一个能导入待测纯函数的测试 | 模块或导入边界尚不存在 | 配置后端测试发现规则，并仅暴露必要的测试入口 |
| 0.2 | `frontend/src/__tests__/agentActivity.test.jsx` 中一个渲染最小活动卡片的测试 | 缺少 Vitest/React Testing Library 脚本或组件 | 增加最小测试依赖、测试脚本和测试环境配置 |

测试基础设施通过后，先运行这两个最小测试确认均为绿；之后才开始功能测试。若现有项目已存在未记录的测试命令，实施前应在不改动生产代码的前提下将本表替换为实际命令。

## 测试边界

为避免测试复杂的嵌套闭包或真实模型，生产代码必须由失败测试驱动出三个可替换边界：

- `build_exception_analysis_context(...)`：纯函数，只提取并脱敏异常分析上下文。
- `analyze_exception_for_user(...)`：异步边界，接收安全上下文与可注入的模型调用器，返回已校验的结构化分析或空结果。
- `build_activity_event(...)`：纯函数，根据可观察生命周期事件生成 `activity` 负载。

`stream_agent_events(...)` 继续负责时序编排，但测试通过伪造 Agent 事件流和注入的分析器验证其输出。不调用真实模型、网络工具或真实浏览器。

## 后端 TDD 循环

### 1. 安全上下文提取

**Red：** 先写测试，输入包含异常、原始工具参数、授权字段、长文本和部分回答。

断言：输出只保留异常摘要、活动工具名、有限数量的工具名/错误摘要、近期工作状态和长度受限的部分回答；不得包含令牌、授权头、密码字段或原始 traceback。

**Green：** 实现最小白名单和长度限制，测试通过即可。

**Refactor：** 仅在多个测试共享敏感字段判断时提取通用脱敏函数。

### 2. 有效模型分析优先

**Red：** 写入一个假分析器，返回四个完整字段的 JSON：发生情况、可能原因、完成情况、下一步。断言最终 `error` 事件使用这些字段形成中文说明，而不是规则化兜底。

**Green：** 实现解析和字段存在性校验，仅支持该测试要求的结构。

**Refactor：** 将用户文本格式化与 JSON 校验分开，但不得扩大允许的原始字段范围。

### 3. 模型失败与格式失败兜底

每一种失败原因单独一轮 Red/Green：

| Red 测试 | 断言 |
| --- | --- |
| 分析器抛出超时或运行时异常 | 流仍发送安全规则化说明和 `done`，不抛出第二个异常 |
| 分析器返回不可解析文本 | 拒绝文本并使用规则化兜底 |
| JSON 缺少任一必填字段 | 拒绝结构并使用规则化兜底 |
| JSON 包含 traceback 或疑似敏感字段 | 拒绝或清理不安全内容后使用安全兜底 |

每轮 Green 只增加该失败类型必需的处理；四轮都绿后才合并重复分支。

### 4. 工作动态事件生成

每个状态是一轮独立 TDD：

| 顺序 | Red 测试输入 | 断言的 `activity` 输出 |
| --- | --- | --- |
| 4.1 | 请求开始 | `state=understanding`，说明正在理解任务，包含已用时间 |
| 4.2 | 工具开始 | `state=working`，摘要描述真实工具执行，不含原始参数 |
| 4.3 | 工具结果已处理 | 包含已验证结果摘要；仅在存在证据时包含 `evidence` 或 `judgment` |
| 4.4 | 修复重试 | `state=judging` 或 `working`，说明已发现问题并正在调整处理方式 |
| 4.5 | 正常结束 | `state=completed`，时间线可收束 |
| 4.6 | 终止异常 | `state=blocked`，判断引用已校验的用户异常分析 |

Green 阶段禁止从模型 token 或隐藏思维链构造文案；文案只能由请求、工具生命周期、工具结果摘要和异常分析等可观察事实得出。

### 5. 事件流顺序与心跳合并

**Red：** 用可控的异步伪 Agent 依次产出“工具开始、多个超时心跳、工具结果、结束”。断言：

- 首项是 `understanding` 活动。
- 工作阶段以 `activity` 形式出现，且与实际工具生命周期一致。
- 多个同阶段心跳只更新最近工作项，不追加多个用户可见时间线项。
- `completed` 在 `done` 之前；终止失败时 `blocked` 在 `error` 和 `done` 之前。

**Green：** 只引入必要的最近活动键和替换逻辑。

## 前端 TDD 循环

### 6. SSE `activity` 解析

**Red：** 在独立的事件分发函数或最小挂载组件测试中送入一帧 `activity` JSON。断言它进入本轮请求的活动集合，且 `text`、`debug`、`tool_call` 和 `tool_result` 的既有处理不变。

**Green：** 仅添加 `activity` 分支与请求内活动状态。

### 7. 默认展开的对话内时间线

**Red：** 使用一条 `working` 活动渲染组件。断言页面可见“Agent 工作动态”、摘要、已确认事实、判断、下一步和进度；组件初始状态不折叠。

**Green：** 实现最小时间线组件与样式，不修改 Debug stream 组件。

### 8. 同阶段更新与终态收束

依次进行三轮 Red/Green：

1. 送入同一工作阶段的新事件，断言最近卡片被更新而非重复追加。
2. 送入 `done`，断言时间线显示完成，历史活动和最终回答仍可见。
3. 送入 `error`，断言时间线显示受阻，并显示后端的用户可读异常判断。

### 9. 回归保护

**Red：** 在渲染工作动态的同时送入 Debug 事件和工具事件。断言 Debug stream 仍可展开，工具调用分组仍存在，工作动态不显示原始工具参数。

**Green：** 仅修正状态隔离或组件组合，不合并用户活动与 Debug 数据模型。

## 每轮执行命令

实施者必须在每个 Red 和 Green 阶段记录实际命令与结果。命令在测试环境建立后固定为项目脚本，例如：

```powershell
# 后端：替换为项目实际配置的单测命令
python -m pytest backend/tests/test_agent_activity.py -q

# 前端：测试环境建立后执行单文件测试
npm --prefix frontend run test -- agentActivity.test.jsx

# 一个功能组完成后
npm --prefix frontend run build
```

Red 阶段必须看到预期断言失败；Green 阶段必须看到相同测试通过。若命令因环境或导入错误失败，先修复测试环境，再重新获得有效的 Red 失败。

## 完成条件

- 每个新增生产函数或行为都有先失败后通过的测试记录。
- 所有异常分析成功与降级路径均由自动化测试覆盖。
- 所有 `activity` 生命周期状态、心跳合并和前端终态收束均有测试覆盖。
- Debug stream、工具事件和任务进度侧栏的回归测试通过。
- 后端测试、前端测试和前端构建均通过，且没有新增警告或错误。
