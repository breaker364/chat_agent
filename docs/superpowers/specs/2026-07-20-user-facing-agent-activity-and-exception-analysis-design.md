# 面向用户的 Agent 工作动态与异常分析

## 目标

让 Agent 失败时的反馈可执行，并让非开发人员能理解每个请求的执行情况，同时不暴露内部思维链或原始诊断数据。

## 范围

- 将异常处理函数从仅依赖规则的解释，改为基于执行证据的 Agent 分析，并保留可靠的规则化兜底。
- 在当前助手回复中增加面向用户的实时工作动态时间线。
- 保留现有 Debug stream、工具调用分组和任务进度侧栏，以展示技术细节。

## 异常分析

事件流在重试后仍无法继续时，后端收集安全的执行上下文：最终异常摘要、当前工具、近期工具调用、已脱敏的工具错误、最近的工作动态和可能存在的部分回答。

后端要求已配置的 Agent 模型生成结构化中文说明，包含以下四项：

1. 发生了什么。
2. 基于证据的可能原因。
3. 已完成和未完成的内容。
4. 建议的下一步操作。

仅当模型回复可解析且包含有意义的用户可读内容时才采用。回复不得包含 traceback、凭据、请求头、原始工具参数，也不得给出没有证据支撑的确定性结论。模型超时、报错、返回格式错误或没有可用上下文时，使用现有的通用分类文案兜底；有效的模型分析绝不能被兜底文案覆盖。

## 工作动态事件契约

后端新增 SSE 事件 `activity`。每个事件负载包含：

- `state`：`understanding`、`working`、`judging`、`completed` 或 `blocked`。
- `summary`：当前工作的简明自然语言描述。
- `evidence`：可选的已验证事实或结果摘要。
- `judgment`：可选的、由证据支撑的判断。
- `next_step`：可选的下一步动作。
- `progress`：可选的 `{ current, total, label }` 对象。
- `elapsed_seconds`：本次请求已耗用的秒数。

工作动态从可观察的生命周期事件生成，而非模型隐藏推理。它描述接收请求、启动或完成工具、处理结果、重试、完成或受阻。连续的心跳更新替换当前工作项，避免时间线无限增长。

## 前端体验

前端为每个活跃请求在聊天流中创建一条 `Agent 工作动态` 时间线。它在请求开始时立即显示，并在请求执行期间保持展开。最新项以自然语言展示当前操作、已确认的证据、判断、下一步和进度；较早的条目保留为按时间排序的记录。

最终回答到达后，时间线收束为完成状态；错误终止请求后，时间线切换为受阻状态。最终回答仍是主要内容。现有 Debug stream 保持独立，继续展示原始运行时信息；工作动态卡片不复制原始参数或原始结果。

## 数据流

1. 后端开始请求，并发送 `understanding` 工作动态。
2. Agent 和工具生命周期事件以可观察的状态和进度更新工作动态。
3. 前端解析 `activity` SSE 帧，将其写入本次请求的活动状态，并与流式助手内容一同渲染。
4. 正常完成时，在 `done` 前发送 `completed` 工作动态。
5. 发生终止错误时，先发送 `blocked` 工作动态，其判断来自详细异常分析；再发送已有的 `error` 和 `done` 事件。

## 测试

- 单元测试：模型返回有效异常分析时，验证其优先于通用兜底。
- 单元测试：模型失败、超时、JSON 格式错误和疑似不安全输出时，验证会得到通用且安全的兜底。
- 流式测试：覆盖请求开始、工具生命周期、正常完成、修复重试和终止失败时的工作动态事件。
- 前端测试：覆盖实时工作动态渲染、心跳替换、完成/受阻收束，以及 Debug stream 的保留。

## 非目标

- 向最终用户暴露私有思维链、工具参数、密钥或原始 traceback。
- 删除或重新设计现有技术 Debug stream。
- 修改与异常恢复或请求状态沟通无关的 Agent 行为。
