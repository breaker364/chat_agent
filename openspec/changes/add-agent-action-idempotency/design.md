## 背景

现状四层机制与缺口:

| 既有机制 | 位置 | 覆盖 | 缺口 |
|---|---|---|---|
| 运行内去重缓存 + 会话级结果缓存 | `tools.py` `_TOOL_DEDUPE_CACHE`、conversation cache | 只读工具按 TTL 复用;副作用工具成功后同参重发被拦 | 失败调用无分类,重复失败无反馈(bash 除外,见未实施草案) |
| 远端变更成功台账 | `mutation_guard.py` `MutationLedger`、`skills.py` 派发前查重 | 同一变更身份运行内不二次派发 | `verified` 自报;无执行后校验;无执行前状态检查 |
| 错误分类重试 | `rag/sources.py` `RemoteSourceError.retryable` | 仅 RAG 远源 | 主循环与其余工具不消费分类 |
| agent 有界修复重试 | `agent.py` 修复路径,`MAX_AGENT_REPAIR_PASSES = 2` | 异常后注入上下文续跑 | 不区分错误类型;参数/权限错误同样占用的修复轮次 |

行为侧证据(来自基准审计):7 条唯一失败命令每条被原样重试一次;`MutationLedger` 的 verified 字段在既有调用链中从未由真实校验产生。

## 目标与非目标

**目标:**

- 任何失败的工具调用结果都可机器判读:携带 `error_category` 与 `retryable`,分类规则通用化(按异常类型与状态语义映射,不涉及具体实体)。
- 修复循环对不可重试错误短路:同一调用不因参数错误、权限错误、策略或业务拒绝反复占用修复轮次。
- 失败指纹反馈覆盖全部工具,每个运行内同一指纹只提示一次。
- 幂等决策可审计:副作用调用的结果与审计事件携带确定性推导的 `action_id`。
- 远端变更的 `verified` 由真实执行后校验产生;目标已满足时跳过派发。

**非目标:**

- 不做崩溃级 at-most-once:台账维持运行内作用域,跨运行幂等仍由会话级 conversation cache 承担;台账持久化列为后续议题。
- 不改变副作用拦截的触发条件(仍是"成功后同参重发"),不放宽或收紧现有预算机制。
- 不改动 SSE 协议、前端、模型配置与提示词结构。
- 不重构 workflow 层的 `attempt_id`(任务级重试),本变更只覆盖工具调用层。

## 决策

### 1. 动作标识沿用参数推导,不引入模型生成的 action_id

重复调用的根源是模型重发,模型生成的标识在重发时必然不同,不能作为幂等键。`build_idempotency_key` 已按"工具/提供方、资源、目标、操作、规范参数"做 sha256 并显式排除模型生成的调用标识,直接复用:工具层以 `_dedupe_key` 为通用动作指纹,mutating skill 以 `build_idempotency_key` 为变更身份,两者统一以 `action_id` 字段名透出到结果与审计事件。附加时间戳或任务/步骤绑定会破坏"同一逻辑动作"的判定,不采纳。

### 2. 错误分类在工具层收敛,修复循环只消费字段

新增通用分类映射(模块级常量:异常类型/状态语义到 category 与 retryable 的映射,属仓库允许的通用模式常量),在工具包装层把异常与失败结果规范化为带 `error_category`、`retryable` 的结构。类别初版收集:timeout、network、rate_limited(可重试);invalid_arguments、permission_denied、policy_denied、budget_denied、not_found、business_rejected(不可重试);未知异常默认可重试并维持现状修复路径,避免误判提前终止任务。agent 修复循环读取最近失败记录的 `retryable`:为假且同一调用指纹已失败过时,不再重复注入相同调用;为真时维持有界修复。

### 3. 失败指纹泛化为工具层通用行为

bash 草案(未实施的 fix-agent-tool-reliability 第 3 项)在 bash 工具内维护命令哈希计数。本变更把它上提为包装层通用行为:以动作指纹为键记录失败次数,第二次失败在结果追加一次性反重试提示,第三次起不堆叠;成功调用清空计数。bash 草案先行落地时,其实现迁移到通用路径,要求不冲突。

### 4. post-check 用真实回读,校验失败不记成功

`MutationLedger.record_success` 增加必填校验来源:mutating skill 派发成功后执行 verify 回调(按资源类型重读目标状态,与期望内容摘要或版本比对),比对通过才以 `verified=True` 入账;回读失败或不一致时,结果标记 `verification_failed` 返回给模型,不入成功台账,由运行按既有 blocked 路径处理。无法回读的资源(无读取通道)退化为 `verified=False` 入账并在结果中明示未验证,不伪造校验结论。这把 `safe-remote-mutation-guard` 草案中"读回校验失败即 blocked"的要求落到实现。

### 5. pre-check 仅在目标状态可读且精确匹配时跳过

派发前回调读取目标当前状态:仅当与期望结果精确匹配(内容摘要一致或版本已到达)时跳过派发,结果标记 `already_satisfied` 并照常入台账(视为已完成动作的复用,语义等同查重命中)。匹配不精确时不阻塞派发——pre-check 的职责是消除"已完成还重做",不是猜测意图,宽松跳过会有漏写风险。

## 风险与权衡

- **错误分类误判**:把可重试错误判为不可重试会提前终止本可通过改参恢复的任务。缓解:不可重试名单只收窄语义明确的类别,未知异常默认可重试;基准复测关注 blocked 率不升高。
- **post-check 依赖回读通道**:回读引入额外一次远端读取,且部分资源无读取通道。缓解:仅 mutating 派发执行,读取失败退化为明示的 `verified=False`,不阻塞主流程。
- **指纹提示噪声**:对任务性失败(先失败再修是任务设计的一部分)可能追加无意义提示。缓解:提示只在同指纹第二次失败出现一次,且只陈述事实与建议,不强制。
- **与两个在途草案的协调**:`fix-agent-tool-reliability`(bash 指纹)与 `stabilize-agent-execution-p0`(校验与预算语义)先行实施时,本变更的实现迁移到其通用路径;三者的验收标准不冲突,本变更的回测纳入两者的复测任务清单。
