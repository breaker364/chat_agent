## 背景

现有 agentic-research 运行时是一个回答前的 coordinator。它创建完整工具集，把 `knowledge_search` 交给内部适配器，然后从主 ReAct Agent 中移除该工具及其他证据工具。coordinator 的模型调用不会显示为 Agent 工具事件，`main.py` 又把 coordinator 异常转换为泛化的“没有结果”。在 `session-1786604489093` 中，Agent 因此看不到 `knowledge_search`，误报工具不可用，随后通过 Python 检查 `knowledge_base/index/chunks.json`。

系统仍应采用通用、由模型驱动的来源选择，不能增加实体、域名或关键词到来源的硬编码。个人知识必须通过已注册的检索服务访问，不能直接读取磁盘索引。

## 目标与非目标

**目标：**

- 让主 Agent 实际看到的工具 schema 与系统已注册的证据工具一致。
- 让 Agent 在执行任何证据路由前，先判断请求能否直接回答。
- 将 `ModelResearchPlanner` 作为有边界、可观测的 Agent 工具，用于不明确请求的二级路由判断。
- 用户明确要求知识库或联网搜索时，不经过中间 planner，直接执行对应工具。
- 保留来源策略、调用预算、只读边界、引用和简洁的会话可观测性。
- 防止把 RAG 内部索引文件当作检索回退路径。

**非目标：**

- 不替换混合 RAG 实现、向量存储或排序模型。
- 不要求所有事实问题都检索，也不要求直接回答前必须调用 planner。
- 不暴露 planner 的思维链、原始证据或服务商凭据。
- 不允许规划工具执行任意工具或修改知识库数据。

## 技术决策

### 1. 保留主 Agent 工具 schema 中的证据工具

当工具注册成功时，`build_agent()` 应将 `knowledge_search`、`read_file`、`list_directory`、`get_file_info`、`web_search` 和 `web_fetch` 传给 ReAct Agent。当前“移除证据工具”的逻辑应删除或替换，不能因为启用了规划能力而造成工具可用性与工具可见性不一致。

工具函数继续使用现有输入输出契约。策略和预算通过绑定请求上下文的轻量包装器执行。包装器在调用底层服务前检查来源是否允许，违规时返回结构化结果。

备选方案：保留隐藏 coordinator，只改善错误提示。这样仍然阻止 Agent 检查和选择来源，也无法清楚证明用户明确指定的工具是否被执行，不符合“由 Agent 负责来源选择”的要求。

### 2. 将 planner 注册为只读 Agent 工具

新增 `plan_research_route` 工具，由 `ModelResearchPlanner` 提供能力。它接收有边界的请求文本和已解析的策略，调用 planner，校验返回的 `ResearchPlan`，只返回以下路由字段：

```json
{
  "requires_evidence": true,
  "source_sequence": ["personal_knowledge", "workspace", "web"],
  "query_or_scope": "...",
  "freshness_need": "stable",
  "success_criteria": ["..."],
  "status": "ok"
}
```

planner 响应无效或服务调用失败时，返回有边界的 `status` 和 `error_category`，不得执行任何证据工具。Agent 可以据此澄清问题、选择策略允许的来源，或说明限制。planner 只提供建议，不能返回任意工具名，也不能越权执行工具。

备选方案：让 planner 继续作为隐藏的前置调用。这样会保留当前的可观测性问题，也无法证明 Agent 是主动遵循还是跳过了建议。

### 3. 先处理显式来源，再由 Agent 负责两阶段路由

提示词和工具契约规定以下顺序：

```text
用户明确指定知识库或联网搜索
  -> Agent 直接调用对应的已暴露证据工具

否则
  -> Agent 判断能否在没有外部证据的情况下回答
  -> 直接回答，或调用 plan_research_route
  -> Agent 调用策略允许且建议使用的证据工具
  -> Agent 根据返回的引用和结果组织答案
```

显式来源选择来自请求策略和用户语义意图，而不是静态实体或关键词映射。`knowledge_policy=required` 代表明确选择个人知识。用户明确要求联网搜索时，除非请求策略禁止联网，否则应优先执行该选择。多个来源冲突时，Agent 遵循用户给出的顺序；只有意图无法安全协调时才请求澄清。

Agent 不得在用户已明确指定来源后调用 `plan_research_route`，也不应仅为了证明可以直接回答而调用 planner。

### 4. 在提示词之外执行策略、预算和内部索引边界

请求上下文携带已解析的 `knowledge_policy`、可选的来源覆盖项和调用计数。证据工具包装器执行以下规则：

| 策略或条件 | 包装器行为 |
| --- | --- |
| 必须使用个人知识 | 允许 `knowledge_search`；除非用户明确允许，否则禁止自动回退到联网或工作区检索。 |
| 禁用个人知识 | 拒绝 `knowledge_search`，且不调用底层服务。 |
| 达到来源调用上限 | 返回预算耗尽结果，不再调用服务。 |
| 访问内部 RAG 索引路径 | 在回答生成期间拒绝文件和 Python 读取，将知识库访问导向 `knowledge_search`。 |

内部索引保护应根据配置的知识库路径派生，通用地覆盖 `index` 目录和检索相关文件，而不能写死具体文档名称。该保护只作用于回答生成流程，不能破坏有权限的导入、建索引和维护流程。

备选方案：只依赖提示词禁止读取。之前的会话已经证明，模型可能通过文件和 Python 工具绕过提示词约束。

### 5. 在标准工具事件之外保存有边界的路由记录

planner 工具和证据包装器使用现有 Agent 工具事件，因此会出现在会话 transcript 中。系统另外保存简短的 `research_route` 事件，包含策略、决策类别（`explicit`、`direct`、`planned`）、planner 状态、来源尝试和终止错误类别。不保存 planner 理由、模型消息、原始摘录、原始工具 payload 或凭据。

应移除研究路由周围的裸异常吞没逻辑。未知异常使用关联 ID 写入日志，并转换为结构化的 `planner_error` 或 `provider_unavailable` 结果，同时持久化到会话。

## 风险与权衡

- [Agent 在不明确请求中跳过 planner 直接检索] -> 系统提示词要求自动证据检索前执行二级 planner；使用脚本化 Agent 测试验证调用顺序。
- [额外 planner 调用增加延迟] -> 直接回答和显式来源请求跳过 planner；每次路由最多执行一次有边界的 planner 调用。
- [工具暴露后意外检索增多] -> 策略和预算包装器、工具描述及引用要求共同限制权限。
- [阻止索引读取影响维护] -> 只阻止回答生成期间访问配置的内部检索路径；通过导入、同步和建索引回归测试覆盖维护流程。
- [planner 建议了不合适的来源] -> planner 只提供建议；Agent 仍负责在策略允许的来源中选择和执行。

## 迁移计划

1. 先增加回归测试，复现当前隐藏工具导致的失败。
2. 在不修改现有 RAG 服务的前提下，新增 planner 工具和请求级包装器。
3. 将证据工具暴露给 ReAct Agent，停用回答前隐藏 coordinator 的执行路径。
4. 更新提示词和会话事件，验证流式和同步接口的直接回答、显式来源和自动路由场景。
5. 继续使用 `agentic_research.enabled` 作为发布开关；关闭时保留直接证据工具能力并跳过 planner 注册。
6. 回滚时关闭该开关或恢复 Agent 构建逻辑，不需要迁移知识文档或索引数据。
