## 背景

三轮基准测试(基础 6 任务、长流程 LP 系列 10 任务、多工具 MT 系列 10 任务)共产生约 440 次工具调用。严格审计(command_failed / budget_denied / Traceback / exit_code / Errno 等全模式扫描 + 参数检查)确认 25 次失败调用与 2 次 blocked 运行、1 次进程静默崩溃。失败构成:

| 失败类别 | 次数 | 根因位置 |
|---|---|---|
| bash 调用 `python`/`python3` 不存在(exit 127) | 14 条记录(7 条唯一命令) | bash 工具子进程 PATH 缺虚拟环境 |
| 源调用预算拒绝(`source_call_budget_exhausted`) | 11 条 | `tools.py` 硬编码 `{personal_knowledge: 1, workspace: 2, web: 2}` |
| 任务性失败(MT4/LP5 先跑失败再修) | 若干 | 任务设计,不计入 |

另有两项运行级故障:Windows 会话保存改名竞争(WinError 5,已由 028562d 修复保存侧,但恢复候选仍不可见)与知识栈加载时后端进程静默退出(1 次,无 traceback)。

行为侧证据:7 条唯一失败命令每条被原样重试一次;agent 在文件操作上偏好 bash(cat/echo/mkdir)而非专用 read_file/write_file,直接放大了问题 1。

## 目标与非目标

**目标:**

- bash 工具中 `python`/`python3`/`pip` 可直接解析到当前虚拟环境解释器,消除 exit 127。
- 源调用预算可通过 runtime_config 按类别配置,默认值适配长任务(多阶段、多次读文件)。
- 同一命令第二次失败时,工具结果携带明确的反重试提示;系统提示固化两条行为约束。
- 被阻塞运行的完整上下文(含 assistant 回复)在下次加载会话时自动恢复可见。
- 原生崩溃留下可诊断输出;知识栈模型在启动阶段完成预热。

**非目标:**

- 不修改模型配置与提示词的其余部分,不调整工具集合。
- 不实现通用任务级重试框架(仅针对命令失败提示与持久化恢复)。
- 不把知识栈迁移到子进程隔离(记录为后续议题,本轮只做预热与故障可诊断)。
- 不改动前端。

## 决策

### 1. bash 环境注入用 `sys.executable` 推导,不引入配置项

后端本身运行在项目虚拟环境中,`sys.executable` 的父目录即解释器所在目录。bash 工具构造子进程环境时,将该目录前插到 `PATH`,并设置 `VIRTUAL_ENV`。推导式实现天然适配任意 venv 布局,无硬编码路径(符合仓库泛化性约束)。

备选方案是在系统提示中写死解释器绝对路径。它依赖部署位置、跨机器脆弱,且不解决 `pip` 等伴生工具,不采纳。提示词层面仍会补充一条"运行 Python 优先使用 run_python_file 工具"作为引导,与环境修复互补。

### 2. 预算配置走 `agent.source_call_limits`,默认放宽一档

读取顺序:runtime_config 的 `agent.source_call_limits` → 现有默认。默认值从 `{1, 2, 2}` 放宽为 `{personal_knowledge: 3, workspace: 6, web: 4}`:基准数据显示长任务对 workspace 读取的合法需求为 3-6 次,web 主题对比类任务为 2-4 次。预算防爬取的保护意图保留,仅上调阈值并开放覆盖。

配置解析要求:整数字典、仅接受三类键、非法条目忽略并回落默认;启动日志打印生效值,便于核对。

### 3. 失败命令反馈在工具层实现,提示词只做引导

bash 工具在运行内维护 `command_hash → 失败次数`;同一命令第二次失败时,在返回结果 JSON 追加 `retry_hint` 字段:"该命令此前已以相同形式失败,请勿原样重试;运行 Python 请改用 run_python_file 工具"。放在工具层而非模型层的原因:模型对重复失败不自省是已观测事实,工具结果的显式提示比提示词约束更可执行;提示词同步增加一句约束作为第一道防线。

成功调用不携带该字段;提示只追加一次,失败第三次起不再重复堆叠。

### 4. 恢复候选在加载侧采纳,而不是在保存侧重试更多次

028562d 已让保存侧对瞬时锁重试,但重试耗尽后 `session.tmp-*.json` 恢复候选被保留且无人消费(blocked 运行的回复因此不可见)。方案:`load_session` 读取 `session.json` 之前扫描同目录恢复候选,若存在且修改时间更新,则将其改名为正式文件并加载(记录一条 warn 日志)。前端 3 秒轮询天然触发加载,阻塞运行的回复会在数秒内自动出现。

备选方案是保存侧最终失败时退化为非原子直写。它引入半截 JSON 风险且与既有"保留恢复候选"契约冲突,不采纳。

### 5. 知识栈:faulthandler + 启动预热,不做子进程隔离

崩溃发生在权重加载完成后、无 traceback,指向原生层问题。本轮做两件低成本事:`faulthandler.enable()` 使硬崩溃在 stderr 留下原生栈;应用启动即后台预热知识栈(触发重排序/嵌入权重加载),把崩溃面从"首个用户任务运行中"移到"启动阶段",且预热失败只记日志不阻塞服务启动。子进程隔离改造收益高但改动大,列为后续议题。

## 风险与权衡

- **预算放宽可能放大爬取行为**:默认 workspace 从 2 到 6 后,失控任务的读取上限提高;预算机制本身保留,且可按部署覆盖,风险可控。
- **恢复候选采纳可能"回滚"新保存**:采纳条件限定为"候选 mtime 更新于 session.json",正常流程下保存成功即不存在更新候选,不会触发;失败场景下候选正是最新完整状态。
- **提示词新增约束可能影响其他行为**:仅追加两句工具使用规范,不动其余策略文本;基准复测关注回归。
